# Security review: Areza Secret (2026-10-12)

> **Historical.** Written against the pre-release code (then called Areza Secret, CLI `azsecret`); file names and line
> numbers refer to that version. Status of each finding: [../security-reviews.md](../security-reviews.md).

Scope: `src/worker/*`, `src/shared/*`, `src/web/app.ts`, `site/build.ts` + `site/copy.ts`, `cli/azsecret.ts`, the
`areza-secret` skill, against `docs/specs/secret-drop.md`. Read-only. I ran `bun test` (11 pass) and three local
experiments in a scratch dir: envLine output through real dotenv parsers, the `push` remote script on temp files,
and Bun `fetch` on a cross-origin redirect. Nothing was deployed and no remote service was called.

**Note:** `CHANGELOG.md` says 0.1.0 is already live. That makes finding 1 urgent.

**Verdict:** the core design holds up.
- Burn-after-read is atomic: the Durable Object does get, check and put with no non-storage await in between.
- Fragments cannot reach the server or a Referer.
- No HTML sinks exist (`innerHTML` and the like are absent; every dynamic string is a text node).
- The CSP is tight, there is no ambient-credential CSRF surface, and the server stores only hashes of tokens.
- age usage is correct: hybrid identity, armor, authenticated decrypt, and the bech32 regexes match the charset.

The problems are in the CLI, the abuse controls, quotas, and some claims on the page.

## Confirmed (verified in code or by experiment)

### 1. HIGH: `azsecret open` sends the owner token to whatever host the link names
- **Where:** `cli/azsecret.ts:130-134` (`api()` adds `Authorization: Bearer <owner token>` to every call, whatever the base) and `cli/azsecret.ts:342-357` (`open` uses `url.origin` from the pasted link, `http:` included).
- **Scenario:**
  1. A "client" emails `https://secret-areza.digital/s/<id>#AGE-SECRET-KEY-PQ-1...`, or an `http://` link.
  2. The skill tells the agent to run `azsecret open '<link>' --env ... --to ...`.
  3. The attacker's server receives the owner token and the item `auth`.
  4. With the token, the attacker creates request links that show "Patvirtinta: Areza Digital" and **no** anonymous-phishing warning, sends them to Areza clients, and collects their credentials.
  5. The token also bypasses every per-IP limit and the global cap.
  6. The attacker also chooses the value that lands in the env file.
- **Fix:**
  - Send `Authorization` only when the target origin equals the configured `BASE` origin and uses https.
  - In `open`, refuse a link whose origin is not `BASE` (allow an explicit `--allow-origin` that still never sends the token).
  - Add `redirect: "error"` (see 11).
  - If `open` was ever run on a non-Areza link, rotate `OWNER_TOKEN_SHA256`.

### 2. MEDIUM: anyone who sees a request link can answer it first, and the requester cannot tell or recover
- **Where:** `src/worker/box.ts:68-74` (first fill wins; the sender is not authenticated) and `src/worker/index.ts:109-113`.
- **Scenario:**
  1. The `/r/<id>` link travels by email, as the page recommends.
  2. Anyone with access to that mail fills the request first: a compromised mailbox, a forwarded thread, a CC.
  3. They encrypt to the public recipient a plausible value they control, for example their own SMTP, S3 or webhook credentials, so the client's data flows to them.
  4. The real client gets "This request has already been answered".
  5. The requester `pull`s, then `push`es the attacker's value to production.
- **Fix:** the share link can't carry a secret, so make the race visible and recoverable:
  - On 409, show the sender the fill time and "if this wasn't you, tell the requester now".
  - Give the owner a "reject answer and reopen" action (owner `auth`; clears the ciphertext and sets state back to `open`) in both the web page and the CLI.
  - Have `pull` print the fill time so the requester can confirm it with the client.

### 3. MEDIUM: no takedown path, although the FAQ promises one; anonymous request links make an Areza-branded host a phishing tool
- **Where:**
  - `src/worker/index.ts:121-126` and `src/worker/box.ts:87-95`: revoke needs the item's auth or manageToken. The owner token does not help.
  - `site/copy.ts:170` / `:453` promise "We remove requests used for fraud".
  - `src/shared/protocol.ts:88-93`: `cleanLabel` strips only C0 controls and DEL.
- **Scenario:**
  1. Someone creates `/r/<id>` labelled "Swedbank: patvirtinkite prisijungimą, įveskite Smart-ID PIN" and spams it.
  2. The page is on secret.areza.digital with TLS and Areza branding. The warning is a notice below the label.
  3. You receive the abuse report and have no way to remove the link. It lives for 7 days, and Safe Browsing may flag the hostname.
- **Label spoofing:**
  - A label can imitate the badge, e.g. "✓ Patvirtinta: Areza Digital".
  - It can carry bidi overrides (U+202E), zero-width characters, and an unlimited stack of combining marks inside 140 code points. A tall stack of marks can draw over the warning.
- **Fix:**
  - Let `revoke` succeed when `isOwner` is true, recorded as a distinct `removed` state that the fill page explains. Add `azsecret takedown <id>`.
  - For anonymous labels:
    - Strip `\p{Cf}` and `\p{Cc}`, normalise to NFC, and cap combining marks.
    - Reject labels containing `areza`, `patvirtint`, `verified` or check-mark characters.
    - Consider a short keyword list: PIN, Smart-ID, bank names.
  - Render `warnAnon` above the label, and clip `.app-title` overflow.

### 4. MEDIUM: every request writes to Durable Object storage, including rejected and static requests, so one client, or plain polling, can use up the free-tier quota
- **Where:**
  - `src/worker/limiter.ts:14-16`: a `put` on every hit, even after the limit is exceeded.
  - `src/worker/index.ts:94`: each GET calls the limiter DO and the item DO.
  - `src/web/app.ts:19,204-212`: polling every 10 s.
  - `wrangler.jsonc:13`: `run_worker_first: true` makes every font, CSS and JS request a Worker invocation.
- **Scenario:**
  - The spec targets the free tier, which allows about 100k Durable Object rows written per day.
  - A loop of `GET /api/items/<any 22-char id>` writes one row per request and keeps writing after it hits 429.
  - About 100k requests stop create, open and fill for everyone, the Areza CLI included, until 00:00 UTC.
  - No attacker is needed: each visible owner or send-status tab writes about 8,640 rows a day.
  - Two polling tabs behind one office NAT exceed the 600/h read limit. The page then stops updating without saying why (`app.ts:208` swallows the 429).
- **Fix:**
  - Don't write once `count > limit`.
  - Do per-IP limiting with the Workers Rate Limiting binding (in memory) or a WAF rate-limiting rule on `/api/*`, before any Durable Object call.
  - Poll every 30-60 s with backoff, and show a "paused" notice on 429.
  - Limit `run_worker_first` to `/api/*` and the app paths, and serve the static security headers from `dist/_headers`.
  - Or move the account to Workers Paid.

### 5. MEDIUM: the per-IP limit is bypassed with IPv6, and the global cap is cheap to exhaust
- **Where:** `src/worker/index.ts:212-217` (keyed on the full `CF-Connecting-IP`) and `:37-38`.
- **Scenario:**
  - One host rotates addresses inside its /64 and gets a fresh 30 creates/hour for each address.
  - 5,000 creates use up `GLOBAL_DAILY_CREATES`, and every anonymous user of the public tool gets 429 until UTC midnight.
  - On IPv4 it takes about 7 addresses: 30 creates/h for 24 h each.
- **Fix:**
  - Key IPv6 by its /64 (/56 is safer).
  - Make the global cap hourly so an exhaustion heals within an hour.
  - Put the first line of defence at Cloudflare (see 4).

### 6. MEDIUM: "Delete now" shows "deleted" even when the server says the link was already read
- **Where:**
  - `src/web/app.ts:367-370` ignores `outcome.data.state`. The server answers `{state:"read"}` with 200 (`src/worker/box.ts:92`).
  - Same pattern at `src/web/app.ts:697-701`.
- **Scenario:**
  1. A sender pastes the link to the wrong person.
  2. They return to the tab. Polling is paused while the tab is hidden (`app.ts:206`).
  3. They click "Delete now" twice before the next poll, but the wrong person has already opened the link.
  4. The page says "Status: deleted", so the sender doesn't rotate the credential.
- **Fix:** branch on `outcome.data.state`. If it is `read`, fetch the item again and show `statusRead` with `readAt`.

### 7. MEDIUM: the CLI burns the secret before checking it can save it, and the value is then lost
- **Where:**
  - `cli/azsecret.ts:297-309`: `decryptInto` runs open (burn), then decrypt, then `saveValue`.
  - `cli/azsecret.ts:342-358`: `open` checks no target before burning.
  - `cli/azsecret.ts:186-190`: the presence, name-pattern and multi-line checks all run after the burn.
  - `cli/azsecret.ts:311-322`: `pull` checks that a target is present but not that it is valid.
- **Scenario:**
  - `azsecret open '<link>'` with no `--env/--to/--raw`, or `--env bad-name`, or a multi-line value with `--env`, burns the link and saves nothing. The e2e step "multi-line value refused for --env (exit 7)" does exactly this.
  - An unwritable `--to` path or a bad `pull --env` does the same.
  - The sender sees "opened" and assumes the secret arrived.
- **Fix:**
  - Validate the whole target before the open call: name pattern, presence, parent directory writable.
  - After a successful open, never drop the plaintext. If the env write fails, `writePrivate` it to `$HOME/recovered/<id>` (0600), print the path and exit non-zero.

### 8. LOW: env-file quoting does not round-trip outside `sh`, so some secrets are saved corrupted
- **Where:** `cli/azsecret.ts:160-164` (`envLine`), `:189` (`.trim()`) and `:197-207` (`readEnvValue`).
- **Tested** with values written by `envLine`:
  - Node's built-in `util.parseEnv` reads `p"w` back as `p\` (truncated), `a\nb` as `a\` plus a newline plus `b`, and `` x`y `` as `` x\`y ``.
  - `bun --env-file` reads `p\"w`, `a\\nb` and `` x\`y ``.
  - Only `sh` reads them back correctly. The comment says both shells and dotenv parsers read the line back unchanged.
- **Other problems:**
  - `.trim()` drops leading and trailing spaces from passwords.
  - `readEnvValue` takes the first duplicate, while `sh` uses the last.
  - `readEnvValue` keeps an inline `# comment` in unquoted values, and `push` then ships it.
- **Scenario:** a client's DB password contains `"`. `pull` reports success, and the Node app receives a truncated password.
- **Fix:**
  - Write `NAME='value'` when the value has no `'`. Tested: `sh` and Node read single-quoted values verbatim; Bun still expands `$` inside single quotes.
  - For values containing `'`, or `$` when the consumer is Bun, fall back to `--raw` (see 7) instead of guessing.
  - Strip only the one trailing newline.
  - Take the last match in `readEnvValue`.
  - Add a round-trip test through `sh`, `util.parseEnv` and `bun --env-file`.

### 9. LOW: `push` leaves old and new secrets readable and reports success on odd targets
- **Where:** `cli/azsecret.ts:415-434`.
- **Tested locally:**
  - A 0644 env file stays 0644 with the new secret in it.
  - `app.env.azsecret.bak` (copied with `cp -p`, so also 0644) keeps the previous value indefinitely. That is the key you are rotating out after a leak.
  - If `--remote` is a directory, `mv` puts a file holding the secret inside it, exits 0, and the CLI says "set NAME".
- **Other problems:**
  - `cat "$tmp" > "$f"` truncates and rewrites in place, which is not atomic.
  - `--ssh` accepts values starting with `-`. For example `-Fx` makes ssh read config `x` from the working directory, and a `ProxyCommand` in it runs locally.
- **Fix:**
  - Refuse when `$f` exists and is not a regular file.
  - Warn or refuse when the file is group- or world-readable, and `chmod 600` the backup.
  - Make the backup opt-in, or delete it on success.
  - Reject a host that starts with `-`, or put `--` before it.
  - Join the script with `;` rather than newlines (csh login shells reject newlines inside quotes).

### 10. LOW: `writePrivate` uses a predictable temp name and follows symlinks
- **Where:** `cli/azsecret.ts:108-114`.
- **Scenario:**
  1. The user runs `--raw /tmp/key.json`, or writes into any other shared directory.
  2. Another local user has pre-created `key.json.tmp-<pid>`, either as a symlink or as a 0666 file they own.
  3. `writeFileSync` writes the secret through it. `chmodSync` then fails with EPERM and leaves the file world-readable.
- **Fix:** create the temp file with `openSync(temp, "wx", 0o600)` and a random suffix (or `mkdtemp` in the same directory), and refuse targets in world-writable directories.

### 11. LOW: the CLI follows redirects and re-sends the `auth` body
- **Where:** `cli/azsecret.ts:137-141`.
- **Tested** on Bun 1.4.2: on a cross-origin 307, Bun drops `Authorization` but re-POSTs the body `{auth}`.
- **Scenario:** a Cloudflare redirect rule or a domain move sends the open/revoke token to another host.
- **Fix:** `redirect: "error"`.

### 12. LOW: `send` prints the link by default, and `open` takes it in argv
- **Where:** `cli/azsecret.ts:291-293` and `:343`.
- **Scenario:**
  - The default output puts a working key into the agent transcript (stored on disk and sent to the model) until the recipient opens the link.
  - `open '<link>'` puts the key in shell history and in `ps`. If the call fails before the burn (429, network), it stays valid there.
  - The skill documents the first case, but the CLI header says it never prints a value.
- **Fix:** make `--clipboard` (or `--out`) the default and require `--print`, and let `open` read the link from stdin or the clipboard.

### 13. LOW: the "intercepted" signal disappears at expiry, and whoever holds a link can make it look sender-deleted
- **Where:**
  - `src/worker/box.ts:36-39` and `:97-99`: everything is deleted at `expiresAt`, including the `read` state.
  - `src/worker/index.ts:123` with `src/worker/box.ts:90`: the link's own `auth` can revoke a send item.
- **Scenario:**
  1. An interceptor opens a 7-day link on day 6.
  2. The recipient tries it on day 8 and sees "does not exist or has expired", with no sign of interception.
  3. That contradicts `copy.ts:48` / `:331` ("anyone opening it later sees when that happened").
  4. An interceptor can also revoke the link, and the recipient then reads "The sender deleted this link".
- **Fix:**
  - At expiry, delete the ciphertext, recipient and label, but keep a `{state, readAt}` tombstone for about 30 days, removed by a second alarm.
  - Accept only `manageToken` when revoking a send item.

### 14. LOW: `IP_SALT` falls back to a constant from the source code
- **Where:** `src/worker/index.ts:215`.
- **Scenario:**
  - If the production secret is missing, IP hashes use `"dev-salt"`, and IPv4 hashes can be reversed by enumerating all 2^32 addresses.
  - Even with the secret set, anyone holding it can reverse them. The hashes are pseudonymous personal data, not anonymous.
- **Fix:** fail closed (500 on `/api`) when `IP_SALT` is unset, and describe the hashes accurately on the page.

## Worth checking (platform behaviour or deploy config the repo can't prove)

### A. MEDIUM: Workers Logs probably store IPs next to item ids, which contradicts the copy
- **Where:** `wrangler.jsonc:28` (`observability.enabled: true`, `head_sampling_rate: 1`) and `copy.ts:162` / `:445`.
- **Problem:**
  - Every invocation is logged with its URL (`/s/<id>`, `/api/items/<id>/open`) and, as far as I know, request headers and `cf` metadata (`cf-connecting-ip`, user agent, city, ASN).
  - That ties an IP to an item and a time for the log retention period.
  - It contradicts "we do not store the IP address itself" (`copy.ts:162` / `:445`) and "no tracking" (`copy.ts:28` / `:311`).
  - The "server sees" list (`copy.ts:58` / `:341`) also leaves out request labels, which are stored in plaintext and returned to anyone who has the id.
- **Check:** open one log entry in the dashboard. Also confirm that `authorization` (the owner token) is redacted.
- **Fix:** set `"observability": {"enabled": true, "logs": {"invocation_logs": false}}`, or turn observability off, or reword the copy.

### B. MEDIUM: "deleted" is not deleted at the storage layer, because SQLite-backed Durable Objects keep 30 days of point-in-time recovery
- **Where:** `box.ts:83,93,98` delete only the live state.
- **Scenario:**
  1. Someone gains deploy rights on this Worker, through a Cloudflare account compromise or a leaked token with Workers edit.
  2. They restore an item to its state before the read.
  3. With the link, which is still in the recipient's mailbox, they decrypt it.
- **Claims affected:** "no second read" and "after expiry both are deleted" (`copy.ts:119,124,402,407`).
- **Fix:**
  - Keep a per-item random wrapping key outside the Durable Object, for example in Workers KV, which has no point-in-time recovery.
  - Store the ciphertext wrapped with that key, and delete the KV key on read, revoke and expiry.
  - Or reword the copy precisely. Either way, enforce 2FA and scoped tokens on the Cloudflare account.

### C. MEDIUM: areza.digital zone features may inject code or cookies into these pages
- **Problem:**
  - If Email Obfuscation, Rocket Loader, Zaraz, Web Analytics auto-injection or Bot Fight Mode are on for the zone, they also apply to this hostname.
  - The footer contains `hello@areza.digital`, so Email Obfuscation would inject `/cdn-cgi/.../email-decode.min.js`. It is same-origin, so `script-src 'self'` lets it run.
  - Bot features set `__cf_bm` and can challenge API POSTs.
- **Claims affected:** "no cookies" and "code only from our domain".
- **Check:** compare the live HTML with `dist/` byte for byte, and check the response headers for `set-cookie`.
- **Fix:** add a Configuration Rule for `secret.areza.digital` that turns these features off.

### D. LOW: the code the server serves is the trust anchor
- **Problem:**
  - A modified deploy can ship JS that sends fragments or plaintext somewhere.
  - For requests, a tampered API or storage can hand the sender a recipient the server chose (`app.ts:589,628`).
  - "Our server never sees" therefore holds only while the deployed code is ours.
- **Fix:**
  - Deploy from CI only, and publish the bundle hash.
  - Append a short recipient fingerprint to the share link (`/r/<id>#<first 16 chars of b64url(sha256(recipient))>`), and have the fill page refuse to encrypt on a mismatch.

### E. LOW: the owner link `/o/<id>#AGE-SECRET-KEY...` sits in browser history and sync for up to 7 days
- **Problem:**
  - Any extension with the `tabs` or `history` permission can read it.
  - `forgetFragment` (`app.ts:189-191`) runs only after the answer is read, and `replaceState` does not remove the earlier global-history entry.
- **Fix:** tell users to keep the link in a password manager. Consider removing the fragment after load, keeping the identity in `sessionStorage`, and adding a "copy private link" button.

### F. LOW: revealed plaintext stays in the DOM
- **Where:** `app.ts:506-515`.
- **Problem:** recent Chrome builds restore some `no-store` pages from the back/forward cache, so Back can show the secret again on a shared machine.
- **Fix:** clear the textarea on `pagehide`.
